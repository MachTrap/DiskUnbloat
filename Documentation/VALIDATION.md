## Scan stuck at zero files on a fresh Mac (consent preflight) — 2026-11-05

- Report: a Release build sent to another Mac asked for permissions, then the scan of the home folder stayed at 0 files while the timer ran.
- Cause (from code; not reproduced on the friend's Mac): before reading anything the coordinator opened ~30 protected folders serially, and each `opendir` blocks until its macOS consent dialog is answered. Nothing reported this, so a dialog hidden behind the window or on another desktop looked like a frozen scan; cancel was only checked between probes, so "Cancelling…" could hang too; and the preflight ran without the enumeration workers' dataless-materialization-off policy, so iCloud-backed Desktop/Documents could block on File Provider.
- Fix: abandonable per-probe `PreflightWaiter` threads with materialization off, `awaitingPermission` events with a scan-screen card and *Skip permission checks* (`skipPermissionChecks`), cancel before any row returns to the chooser.
- Found while testing: a no-op protocol-extension default for `skipPermissionPreflight()` was picked over the actor's method for concrete calls from async code (async overload preference), so Skip silently did nothing; the default was removed.
- Passed: `PreflightWaitTests` (skip through a never-answered probe scans everything; cancel ends the stream while the probe stays blocked; waiter resumes once), hosted `PermissionWaitTests`, core 93 tests, hosted 91 tests, universal Release build, localization audit (551 entries).
- Not verified: the friend's machine itself (which dialog was pending, or whether iCloud was involved) — ask for a retest with the new build; if it still stalls with no card shown, a `sample` of the process is the next step.

## Index bulk load and in-memory aggregation — 2026-11-04

- **Profile first (`~/CODE`, 398 k rows, debug):** after the parallel reader, the index was the bottleneck — inserting cost 3.8 s (name folding 0.54 s and category classification 0.41 s ran serially on the actor; maintaining six secondary indexes per row cost ~2 s versus ~1 s to build them afterwards), and aggregation 2 s (eight correlated subqueries per folder).
- **Changes:** workers compute search names and categories in parallel; a scan bulk-loads its fresh index (secondary indexes dropped, issue marks deferred, both restored once after aggregation or on failure); full aggregation runs in memory in one table pass (release: 0.58 s vs ~2 s SQL); the redundant `parent_index` is gone (`parent_size_index` serves `parent=?`, pinned by a query-plan test). Found and fixed on the way: aggregation ordered folders by path length, so the synthetic group wrapper (`diskunbloat:scan-group`, 22 chars) was summed before any root with a shorter path (e.g. `~/.npm`) and showed stale totals; both aggregation paths now order by real depth.
- **Measured end to end (release builds, same host, `~/CODE`, two runs each, previous commit `c0dd38e` vs now):** full index 4.67 s → 3.22 s (−31 %); default summarizing 2.28 s → 2.0 s (−12 %, now bound by enumeration). Index rebuild (~0.9 s, path index 0.28 s) is the largest remaining fixed cost; `PRAGMA threads` and a larger page cache did not change it and were not adopted.
- **Equivalence on real data:** scanning `~/CODE` (121 k rows) and `~/Library` (311 k rows, hard links and permission errors) and then re-running the SQL aggregation on the same index changed **0** rows. Temporary probe files were removed.
- **Not done — incremental rescans (cache by folder modification date):** a folder's mtime changes only when entries are added, removed, or renamed, not when a file inside grows, so skipping "unchanged" folders would show stale sizes; and the bulk read of a folder already returns every size in the same call a cache check would cost. A sound version needs the FSEvents journal (changed directories since a stored event ID) plus indexes that persist across launches — a separate product decision, not implemented.
- **Tests:** core 84 pass (new `inMemoryAggregationMatchesSQL`, `bulkLoadDefersIndexesAndMarks`, `parentLookupsUseTheCompositeIndex`; `ScanThroughputBench.endToEndStages` added, env-gated). Hosted `DiskUnbloatTests` pass, including `QueuePerformanceBench` (covers folder listings without the old parent index); universal Release build succeeds. The app was not run by hand this round.

## Unsandboxed edition with Full Disk Access guidance (macOS 27 app-data denial) — 2026-11-04

Continuation of the 2026-11-03 app-data round: after `tccutil` resets of both app-data services and the new Info.plist usage keys, the user's retest still saw **no consent dialog** and the same per-path errors (`Firefox`, `discord`), and a **second retest with the App Sandbox removed** kept the same errors — so the previous round's theory (a triggerable consent that nothing requested) is wrong on this machine.

- **Evidence chain (live `/usr/bin/log stream` capture, macOS 27.2 build 26B123):**
  1. Sandboxed, mid-scan worker reads: `sandboxd` consults `kTCCServiceSystemPolicyAppDataDetailed` with **"user interaction not allowed"**, the TCC request fails with `kTCCErrorDomain Code=9` ("access requires indirect object …"), the sandbox denies the read — never a dialog.
  2. Sandboxed, launch-time interactive touch of the touched a third-party app's data with interaction **allowed**: a real tccd `AUTHREQ` fires, then a denial within ~15 ms and **nothing on screen** — the dialog mechanism simply cannot represent this access shape.
  3. Unsandboxed, mid-scan reads: the same `SystemPolicyAppDataDetailed` checks now log the full reason — **"access requires indirect object have an associated app bundle"**. `Firefox`/`discord` are non-sandboxed apps whose `Application Support` directories have no container/app-bundle indirection, so macOS 27 can never build a consent for them; reads are denied with no dialog regardless of TCC stored state.
- **Conclusion:** on macOS 27.2, other applications' app data is unreachable for every app that lacks Full Disk Access — the denial is in the system policy layer, not a revocable TCC decision. This is why real-world disk utilities ship unsandboxed and guide the one FDA grant.

  - `ScanPermissionPreflight.probe` now returns `.readable`/`.containsDeniedChildren` instead of fire-and-forget open; `ScanCoordinator` emits one `ScanEvent.protectedFoldersRefused` when any upfront probe hit refusals; `ScanViewModel` tracks `protectedFoldersRefused` (reset per scan, also fed by branch refreshes).
  - The issues sheet ("Unavailable locations") gains an honest guidance card when refusals were detected: macOS protects these against every app, no dialog exists, Full Disk Access is the supported way to measure them — with an "Open Full Disk Access settings" button (`accessibilityIdentifier` `openFullDiskAccess`). English + Russian strings added; honest per-path issue listing unchanged.
  - The temporary `--diskunbloat-tccprobe` entry-point diagnostic was removed; its finding lives on as the deterministic fixture test below.

## Upfront consent for other applications' app data (macOS 26 SystemPolicyAppData) — 2026-11-03

- **Report:** scanning the home folder produced "Не удалось открыть файл «…», так как у Вас нет разрешения" entries for other applications' data (`~/Library/Application Support/Firefox`, `discord`, …) although the app shows many consent prompts upfront. The user's diagnosis is correct: nothing requested the app-data consent.
- **Mechanism (research):** since macOS 26, reading another application's app data is gated by its own TCC service, `SystemPolicyAppData` ("would like to access data from other apps"), with `NSAppDataUsageDescription` as its usage-description key. The app's preflight probes touched only Apple's own `Application Support` subfolders and the sandbox-container categories, and the Info.plist carried no usage-description keys at all — so the App Data consent could never be triggered, and enumeration hit the per-folder denials instead. (macOS 27 additionally introduces `SystemPolicyAppDataDetailed`; the preflight works the same way regardless.) *Superseded by the 2026-11-04 entry: on macOS 27.2 this consent cannot be triggered for non-sandboxed apps' data at all — the system denies those reads with no dialog; see the Full Disk Access round.*
- **Fix:** (a) `ScanPermissionPreflight` probes `~/Library/Application Support` itself (`.childrenAndBundles`); the probe depth now opens up to four immediate child directories, because Application Support mixes `com.apple.*` and third-party folders in readdir order and only touching another application's data triggers the consent; (b) the app bundle's Info.plist now carries the public usage-description keys for every category the preflight touches — AppData, Desktop/Documents/Downloads folders, Photos, Apple Music, Contacts, Calendars, Reminders, HomeKit.
- Honest limits: a "Don't Allow" answer still produces per-path scan issues — that is the app's honest degradation, never a bug; and the visibility of the system dialog itself is not programmatically verifiable in hosted tests (it needs a real user click on a real dialog). The core file verifies target selection; `plutil -lint` and the Release build verify the keys' syntax and presence.
- Tests: core 73 pass, including the updated `permissionPreflightScopesUpfrontTargetsToSelectedDirectoryAndExclusions` (fixture now contains `Library/Application Support/{Firefox,discord}` and expects the new target). Hosted 78 pass; universal Release build passes; localization audit 517 entries (no new strings).

## Bulk-selection performance round with a benchmark harness — 2026-11-03

- **Report:** after the empty-map fix, the same flow (home scan → rebuildable select → confirm) worked but the queue panel spun "Updating the list…" for minutes; the map updated only gradually.
- **Measurement-first approach:** `DiskUnbloatTests/QueuePerformanceBench` times every stage at field scale (a 32k-row index, 1643 queued entries gathered straight from index rows, ContinuousClock per stage). First runs exposed costs far beyond SQLite's own raw timings (the same shapes ran in single-digit milliseconds through the sqlite3 CLI), isolating the Swift/query-plan contributors.
- **Fixes, each with its measured effect (debug test host, 1643 queued on 32k rows):**
  - Composite `parent_size_index ON nodes(parent, knownAllocated DESC, id)`: the folder listing's `parent=? ORDER BY knownAllocated DESC, id LIMIT n` plan previously degraded to a full single-column size-index scan per folder — root query/summary now measure ~0 ms.
  - Exclusion anti-join: the temp tables now hold **excluded row ids** (`excludedRow(rowId INTEGER PRIMARY KEY)`, filled through one indexed path-band `INSERT … SELECT` per range, exact-path rows included; descendants-only bands for collapsed containers). Every query rejects excluded rows with a `NOT EXISTS(e.rowId = nodes.id)` primary-key probe. The earlier per-path `OR`-clause probes could not use an index and made a whole-table legend build take 13–48 s and a map commit 33 s; now the legend is 34 ms and the map commit with hidden state 124 ms (both were workload-monsters before the round).
  - Map subtraction bucketing: `mapScene` builds an ancestor-keyed `queuedWithin` dictionary once per commit (O(queue × depth)) so every row's visible size is one lookup instead of a scan over the whole queue.
  - Panel gather batching: `CleanupQueueProviding` gained `ancestors(of ids:)` and `childCounts(of ids:)`; the panel resolves hundreds of entry chains in a constant number of indexed `id IN` statements instead of thousands of per-node await hops (11 ms measured for 1643 chains), partial-ancestor detection uses an entries-id set with early chain stop, and child counts arrive grouped (19 ms for 1705 folders). The whole panel rebuild went from minutes in the field to **36 ms** at scale.
  - Membership indexing: the per-render `queueMembership` linear scan is replaced by `QueueMembershipIndex` (an exact-path set plus a folders-with-entries-below set, both rebuilt once per basket change; each lookup is a parent-chain walk), wired through `ExplorerView`/`TreemapView` as a closure; the pre-render membership loop that measured 375 ms at scale is O(depth) now.
  - Cached queue attributes: `estimatedBytes`/`hasUnknownSizes` are recomputed once per basket change instead of per render.
- Bench numbers after the round: attach 44 ms, map commit with hidden 124–126 ms, legend 34–36 ms, panel rebuild #1 36 ms, coalescing 10 ms, application of a 1643-entry queue 73 ms. `CleanupQueueTests`' stub provider grew the batched methods; the folder-refresh flow applies hidden state deterministically before restoring presentation. A legacy test expectation moved with the correct semantics (a queued row's map selection now reliably leaves the selection).

## Empty map after a large quick-select — root causes and fixes — 2026-11-03

- **Report:** home scan (~130 GB), the rebuildable quick-select confirmed (~49–53 GB estimated), the "items were skipped by safety checks" alert appeared, and the object map went completely empty ("No sized items") although only part of the scan was queued.
- **Reproduction:** a temporary env-gated probe inside the real sandboxed app scanned the real home, confirmed the rebuildable tier through `selectItems`, and dumped the pipeline state: 1675 queued entries (49.3 GB), 11 safety-skip refusals — and the explorer's `hiddenPaths` stayed **0** forever, then, once applied, the scene collapsed to `entries=0` while the header still showed the root's visible size. A core-level bisection with the real path list broke between 900 and 1000 paths.
- **Root cause 1 — SQLite expression depth kills the map query.** The map query expressed every queued item as `NOT(path=? OR (path>=? AND path<?))` in one flat conjunction; SQLite rejects parse trees deeper than 1000 with "Expression tree is too large", and `readRows` silently returns `[]` on a prepare failure — so beyond ~1000 queued items the map queried zero rows while the header total (root's visible size) stayed. The raw C-API probe confirmed the exact error.
- **Root cause 2 — the queue→map handoff never fired.** The hidden paths were forwarded to the explorer through a SwiftUI `.onChange` of the whole basket array; in the real flow it never fired, so queued items kept "invisible" state and the map never subtracted them.
- **Root cause 3 — collapsed containers' bytes stayed in their ancestors.** When every direct child of a folder was queued, the folder collapsed to a descendants-only range, but the map's `visibleSize` only subtracted the *path* list, overstating the total and every ancestor tile.
- **Fixes (superseded in parts by the performance round below — see the exclusion anti-join and the cached per-basket accounting):** (a) exclusion temp tables instead of per-path clauses so no parse tree grows with the queue; (b) hidden paths reach the explorer from the model layer (`CleanupViewModel.basketDidUpdate` → `explorer.updateHiddenPaths`) and the hidden application reloads the scene synchronously; (c) collapsed containers subtract the queued children's known sizes from their own tile and every ancestor, so the map total equals the scan minus the queue's estimate; (d) a queued item's map selection now reliably leaves the selection, with the refresh flow applying hidden state deterministically before restoring presentation.
- Tests: core 73 pass (new `MapHidingBulkTests`), hosted 75 pass (`MapAfterSelectionTests.rebuildableSelectionNeverEmptiesTheMap` keeps every unqueued root with exact visible bytes, `workspacesQuickSelectUpdatesTheMapThroughTheQueue` mirrors the full workspace flow, `queueChangesReachTheExplorerFromTheModel` pins the handoff), universal Release build passes, localization audit unchanged at 516 entries.

## Quick-action access repair done the Apple-correct way — 2026-11-03

- **Report:** "All caches" asked for home access, then nothing happened and every other button went dead; the same failure trails persisted.

## Performance optimization pass — 2026-11-01

Hot-path optimizations to scanning, indexing, queries, layout, and cleanup normalization.

- **Insert path:** `ScanIndex.insert` now writes `category`, `rawLogical`, `rawAllocated`, `latestModified`, and `unknownModified` in the single INSERT statement, removing a per-node classification `UPDATE` loop and a per-batch `UPDATE … WHERE <nullable column> IS NULL` that forced a full table scan every batch (an O(n²) hotspot). Synthetic 1M-entry benchmark insert dropped **12.87 s → 9.68 s (~25%)**; aggregate and category queries were unchanged within noise.
- **Enumeration:** the scan no longer requests `totalFileAllocatedSize` or `fileSize`; sizes come from `lstat` (`st_size`, `st_blocks * 512`). "On disk" therefore reflects POSIX block allocation (what `du` reports) instead of `totalFileAllocatedSize`, which also accounted for inode/xattr/fork overhead. This removes the most expensive per-file metadata read; it is not exercised by the synthetic benchmark, so the speedup is only visible on real enumeration.
- **Batch size** raised 512 → 2048 (fewer transactions per scan).
- **Search folding** now uses a fixed `en_US_POSIX` locale (deterministic, cheaper) for both insert and query.
- **Category stats are lazy:** the full `categorySummaries` aggregation only runs in the Types tab; the always-visible legend uses a new lighter `ScanIndex.categoryList` (`SELECT DISTINCT category`).
- **Cleanup plan normalization** is now O(n log n) instead of O(n²).
- **Treemap layout** runs off the main actor and precomputes entry sizes.
